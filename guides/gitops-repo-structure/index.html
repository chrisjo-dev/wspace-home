GitOps 저장소 구조 고르기: 브랜치로 나눌까, 디렉토리로 나눌까

글 Chris Jo, 2026년 10월 22일 작성

이 글은 누구를 위한 글인가

Argo CD로 GitOps를 막 도입했거나 도입을 앞두고, DEV, STG, PRD 세 환경을 Git 저장소 안에서 어떻게 나눌지 정해야 하는 운영 담당자를 위한 글입니다. 저는 지금 환경마다 브랜치를 하나씩 두는 구조로 GitOps 저장소를 운영하고 있습니다. 운영하는 동안 디렉토리로 환경을 나누는 구조와 계속 비교하게 되었고, 그 과정에서 정리한 판단 기준과 브랜치 구조에서 환경 설정을 지키려고 쓴 방법을 이 글에 모았습니다.

정답을 고르는 글은 아닙니다. 두 구조 모두 실제로 많이 쓰이고, 조직의 승인 방식과 운영 인력에 따라 맞는 쪽이 달라집니다. 이 글의 목표는 고르기 전에 무엇을 따져야 하는지 순서대로 짚는 것입니다.

1단계. 앱 저장소와 매니페스트 저장소부터 나눕니다

환경 분리 방식보다 먼저 정할 것이 있습니다. 애플리케이션 소스와 배포 정의를 한 저장소에 둘지, 두 저장소로 나눌지입니다. 저는 나누는 쪽을 기본으로 삼습니다.

저장소담는 것
앱 저장소 (CI)소스 코드, 테스트, Dockerfile, 이미지 빌드와 푸시, SBOM 생성과 취약점 스캔, 릴리스 태그
매니페스트 저장소 (CD)Kubernetes 배포 정의(Helm 또는 Kustomize), 환경별 설정, 환경 승급 이력

나누면 코드 변경 이력과 배포 이력이 섞이지 않습니다. 운영 환경에 무엇이 언제 올라갔는지는 매니페스트 저장소만 보면 되고, 운영망 접근 권한도 이 저장소에만 주면 됩니다. 롤백도 매니페스트 저장소에서 이전 커밋으로 되돌리는 PR 하나로 끝납니다.

매니페스트 저장소는 애플리케이션을 담는 곳이 아니라 클러스터가 유지해야 할 상태를 적어 두는 곳입니다. Helm Chart, Deployment, Service, Ingress, ConfigMap, Secret 참조, 이미지 버전이 여기에 들어갑니다. Argo CD는 이 저장소를 계속 지켜보다가 Git에 적힌 상태와 클러스터의 실제 상태가 다르면 Git 쪽에 맞춥니다. 그래서 이 저장소의 구조가 곧 운영 방식이 됩니다.

2단계. 환경을 브랜치로 나눌지 디렉토리로 나눌지 정합니다

브랜치 구조

환경마다 브랜치를 하나씩 두고, 클러스터마다 다른 브랜치를 바라보게 합니다. DEV 클러스터는 dev/main, STG는 stg/main, PRD는 prd/main을 봅니다. 새 이미지가 나오면 먼저 dev/main이 바뀌고, 검증이 끝나면 dev/main을 stg/main에, 다시 stg/main을 prd/main에 merge합니다. 환경 승급이 Git merge 한 번으로 기록되므로, 운영 환경에 어떤 변경이 들어갔는지 브랜치 이력만으로 따라갈 수 있습니다.

디렉토리 구조

브랜치는 main 하나만 두고, environments/dev, environments/stg, environments/prd처럼 환경을 폴더로 나눕니다. Argo CD는 브랜치 대신 폴더를 바라봅니다. 승급은 대개 버전 값만 바꾸는 PR입니다. DEV에서 1.2.3 검증이 끝나면 STG 폴더의 imageTag를 1.2.2에서 1.2.3으로 고치는 PR을 올리고, merge되면 Argo CD가 STG를 동기화합니다.

항목브랜치 구조디렉토리 구조
승급 방법브랜치 간 merge버전을 바꾸는 PR
환경별 이력브랜치마다 따로 남음한 이력에 섞임
공통 구조 변경merge로 옮겨야 함한 번 고치면 끝
운영 복잡도높음낮음
잘 맞는 조직승인 절차가 중요한 조직SaaS, 플랫폼 조직

3단계. 판단 기준

  • 환경 간 변경 흐름을 승인 기록으로 남겨야 하는가. 변경관리 승인이 필요하고 "PRD에 무엇이 언제 들어갔는가"를 자주 설명해야 한다면 브랜치 구조가 편합니다.
  • Chart나 템플릿 구조를 자주 바꾸는가. 공통 구조 변경이 잦다면 디렉토리 구조가 덜 번거롭습니다. 브랜치 구조에서는 같은 변경을 merge로 계속 옮겨야 합니다.
  • 운영 담당자가 자주 바뀌는가. 브랜치 구조는 merge 순서와 충돌 처리를 이해하는 사람이 운영해야 합니다. 담당자가 자주 바뀌는 조직이라면 이 부담을 먼저 따져 봐야 합니다.
  • 테넌트가 많은가. 테넌트 30개를 상정해 저장소 구조를 정리할 때는 브랜치를 늘리지 않고, 공통 base 아래에 dev-tenant-01, prod-tenant-30 같은 폴더형 오버레이를 두는 안으로 잡았습니다. 도메인, 리소스 쿼터, 환경 변수, 버전을 테넌트 폴더에서만 덮어쓰고, 일괄 승급은 여러 PR을 만드는 스크립트로 처리합니다.

참고로 Argo CD 공식 예제나 플랫폼 엔지니어링 사례는 대부분 단일 브랜치에 디렉토리로 나누는 구조를 씁니다. 처음 정하는데 위 기준에서 브랜치 구조가 꼭 필요한 이유가 보이지 않는다면 디렉토리 구조로 시작하는 편이 부담이 적습니다.

브랜치 구조를 운영하며 겪은 문제와 해결

문제 1. 브랜치를 따로 운영하면 Chart가 갈라집니다

처음에는 merge 없이 환경 브랜치를 각자 독립적으로 관리하는 방법도 생각했습니다. DEV, STG, PRD는 원래 설정이 다르니 서로 영향을 주지 않는 편이 안전해 보였습니다. replica 수, 리소스 limit, DB 주소, Ingress 호스트, Secret은 환경마다 다른 것이 정상입니다.

문제는 공통 구조였습니다. DEV에서 Chart를 추가하거나 템플릿을 고치면 STG와 PRD에도 같은 작업을 해야 합니다. 브랜치가 독립적이면 이 작업을 사람이 세 번 반복해야 하고, 한 번만 빠뜨려도 DEV는 Chart v3, STG는 v2, PRD는 v1인 상태가 됩니다. 그러면 한 환경에서만 나는 문제를 분석하기 어려워지고, 공통 설정 하나를 넣을 때도 환경마다 따로 검증해야 합니다. 그래서 환경별 값은 다르게 두되 Chart, 템플릿, 공통 설정은 merge로 전달하는 방식으로 정했습니다.

문제 2. merge하면 운영 설정이 개발 설정으로 덮일 수 있습니다

merge로 공통 변경을 옮기자 다른 위험이 생겼습니다. DEV는 replica 1개에 CPU limit 500m, 메모리 512Mi로 돌리고 PRD는 replica 10개에 CPU 2000m, 메모리 4Gi로 돌립니다. 아무 장치 없이 merge하면 PRD의 values.yaml이 DEV 값으로 바뀔 수 있습니다.

이를 막으려고 환경별 파일을 merge 대상에서 뺐습니다. 지금 보호하는 파일은 values.yaml과 VERSIONS.md 두 개입니다.

# .gitattributes
/values.yaml merge=ours
/VERSIONS.md merge=ours

# Git 설정 (merge driver 정의)
[merge "ours"]
    name = Keep ours merge
    driver = true

이렇게 하면 STG 브랜치에서 DEV를 merge할 때 두 파일은 STG 내용이 남고, 나머지 Chart와 템플릿 파일은 평소처럼 merge됩니다.

이 장치를 쓸 때 두 가지를 확인해야 합니다. 첫째, [merge "ours"] 정의는 저장소 파일이 아니라 각자의 Git 설정에 들어가므로 merge하는 사람이나 자동화 환경마다 설정되어 있어야 합니다. 둘째, merge driver는 두 브랜치가 모두 그 파일을 바꿨을 때만 불립니다. 예를 들어 STG 쪽 values.yaml이 공통 조상 이후 그대로이고 DEV 쪽만 바뀌었다면, Git은 충돌 없이 DEV 값을 그대로 가져오므로 merge 결과가 DEV 값이 됩니다. 보호 파일이 정말 유지되는지는 시험 브랜치에서 merge해 보고 확인하는 편이 안전합니다.

어느 구조를 고르든 지키는 승급 규칙

  • 환경 승급은 PR과 merge로만 합니다. Argo CD 자동 동기화는 켜 두되, 무엇을 올릴지는 merge 승인으로 통제합니다.
  • 이미지는 태그보다 digest로 고정하고, 사람이 읽을 태그와 digest를 PR 제목에 함께 적습니다. 예: chore(app-foo): bump to v1.4.2 (sha256:...)
  • PRD 설정 폴더나 브랜치는 CODEOWNERS로 운영팀만 승인할 수 있게 합니다.
  • Secret 값은 저장소에 넣지 않고 External Secrets, SealedSecrets, SOPS 같은 도구로 다룹니다.
  • 개발망과 운영망이 나뉘어 있다면 운영망 저장소를 기준으로 삼고, 개발망 변경은 PR로만 넘깁니다. 외부에서 운영망으로 직접 push하지 않습니다.

체크리스트

  • 앱 저장소와 매니페스트 저장소를 나눴다.
  • 환경 승급이 어떤 Git 동작(merge 또는 버전 PR)으로 기록되는지 팀이 같은 답을 한다.
  • 환경마다 달라야 하는 값(replica, 리소스, 주소, 호스트, Secret 참조)과 같아야 하는 구조(Chart, 템플릿)를 구분해 적어 두었다.
  • 브랜치 구조라면 보호 파일 목록과 merge driver 설정이 모든 merge 환경에 있다.
  • 보호 파일이 한쪽만 바뀐 경우에도 유지되는지 시험 merge로 확인했다.
  • PRD 변경은 CODEOWNERS 승인 없이는 merge되지 않는다.
  • 롤백 절차가 "이전 커밋으로 되돌리는 PR"로 정해져 있다.
