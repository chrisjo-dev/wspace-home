로컬 비전 모델 양자화 고르기: Qwen3-VL-8B로 한국어 영수증 읽기

글 Chris Jo, 2026년 10월 22일 작성

이 글은 누구를 위한 글인가

맥북에서 Qwen3-VL 같은 비전 언어 모델로 영수증이나 문서 사진을 읽게 하고 싶은데, Ollama에서 어떤 양자화 버전을 받아야 할지 고민하는 분을 위한 글입니다. 저는 Qwen3-VL-8B-Instruct의 Q4_K_M, Q8_0, FP16 세 버전을 같은 한국어 영수증으로 비교하는 실험을 설계했습니다. 이 글은 그 실험 설계를 바탕으로, 후보를 거르고 공정하게 비교하는 순서를 정리합니다.

미리 밝혀 둡니다. 이 글에는 "어느 양자화가 몇 퍼센트 더 정확했다" 같은 결과 수치가 없습니다. 블로그 원글이 실험 환경과 방법까지만 공개되어 있어서, 확인되지 않은 수치를 적지 않았습니다. 대신 같은 비교를 직접 해 볼 때 그대로 쓸 수 있는 절차와 기록 양식을 담았습니다.

양자화가 바꾸는 것

Qwen3-VL-8B는 이미지를 받아 텍스트를 만드는 80억 파라미터 모델입니다. 세 버전은 모델 구조, 학습 데이터, 파라미터 수가 모두 같고, 각 파라미터를 몇 비트로 저장하느냐만 다릅니다. 비트를 줄이면 파일과 메모리가 작아지는 대신 값이 거칠게 반올림됩니다. 예를 들어 0.0023456789라는 가중치가 Q4에서는 0.002 정도로 저장됩니다.

Ollama 태그양자화, 크기정밀도
qwen3-vl:8bQ4_K_M, 약 5GB4bit, 가장 거친 반올림
qwen3-vl:8b-instruct-q8_0Q8_0, 약 8.2GB8bit
qwen3-vl:8b-instruct-fp16FP16, 약 16GB16bit, 원본 정밀도

qwen3-vl:8b처럼 양자화 표기가 없는 태그가 Q4_K_M이라는 점을 기억해 두면 좋습니다. 이름만 보고 받으면 세 버전 중 가장 작은 버전을 쓰게 됩니다.

1단계. 메모리로 후보를 거릅니다

가장 먼저 볼 것은 내 장비의 통합 메모리에 모델이 들어가느냐입니다. 제 실험 장비는 다음과 같습니다.

장비MacBook Air (2025)
칩Apple M4, CPU 10코어, GPU 10코어, Neural Engine 16코어
메모리32GB 통합 메모리 (LPDDR5X, 대역폭 120GB/s)
OS와 도구macOS Sequoia, Ollama

32GB라면 약 16GB인 FP16까지 올려도 시스템이 쓰는 메모리를 빼고 여유가 있어 세 버전을 모두 후보에 넣을 수 있었습니다. 메모리가 이보다 작다면 모델 크기와 시스템 사용량을 더해 보고 들어가지 않는 버전은 처음부터 뺍니다.

메모리 대역폭도 함께 봅니다. LLM 추론은 계산보다 메모리에서 가중치를 읽어 오는 속도에 묶이는 작업입니다. 120GB/s는 8B 모델을 돌리기에 충분하다고 판단했지만, 같은 모델이라도 크기가 커질수록 한 번에 읽어야 할 양이 늘어 응답이 느려질 수 있으므로 속도는 반드시 직접 잽니다.

2단계. 비교 조건을 하나로 묶습니다

양자화만 바뀌고 나머지는 모두 같아야 비교가 됩니다.

  • 같은 입력. 같은 영수증 이미지를 세 버전에 넣습니다. 저는 카페 영수증을 골랐습니다. 한글 상호명, 영어와 한글이 섞인 메뉴 이름, 금액, 날짜가 함께 있어 한국어 OCR의 어려운 부분을 고르게 담고 있기 때문입니다.
  • 같은 프롬프트. 상호명, 날짜, 품목(이름, 수량, 단가, 금액), 합계를 정해진 JSON 형식으로만 내라고 지시합니다. 설명 없이 JSON만 출력하라고 못 박아 두면 결과를 기계적으로 검사하기도 쉬워집니다.
  • 생각 모드 끄기. Qwen3의 Thinking 모드는 /nothink로 껐습니다. OCR 추출에는 추론 과정이 필요 없고, 생각하는 데 쓰는 토큰이 버전마다 다르면 속도 비교가 틀어집니다.
이 영수증 이미지에서 아래 정보를 JSON 형식으로 추출해줘.
반드시 아래 형식을 지켜줘. 추가 설명 없이 JSON만 출력해.
{
  "store_name": "상호명",
  "date": "YYYY-MM-DD",
  "items": [{"name": "품목명", "quantity": 0, "unit_price": 0, "amount": 0}],
  "total": 0
}

3단계. 무엇을 어떻게 잴지 정합니다

정확도는 실제 영수증 내용과 모델 출력을 필드별로 눈으로 대조합니다. 확인할 지점은 다섯 가지입니다.

  1. 한글 상호명을 빠진 글자나 오탈자 없이 읽는가
  2. 영어와 한글이 섞인 메뉴 이름이 바뀌는 지점에서 깨지지 않는가
  3. 금액의 자릿수와 콤마를 정확히 처리하는가
  4. 날짜를 정해진 형식으로 바꾸는가
  5. 파싱할 수 있는 올바른 JSON을 내는가

필드마다 정확, 부분 오류, 완전 오류 세 단계로 적습니다. 응답 시간은 API 호출 시작부터 끝까지 걸린 시간을 3번 재서 가운데 값을 씁니다. 한 번만 재면 우연히 튄 값 하나가 결론을 좌우할 수 있기 때문입니다. 메모리 사용량은 모델이 떠 있는 동안 ollama ps로 확인합니다.

속도 비교가 생각 모드에 흔들립니다

Thinking 모드를 켜 두면 모델이 답을 내기 전에 쓰는 토큰 수가 응답 시간에 그대로 더해집니다. 양자화에 따른 속도 차이를 보려는 실험에서 이 몫은 잡음이므로 /nothink로 꺼서 조건을 맞췄습니다.

영수증 한 장의 한계

이 실험은 통계를 내려는 것이 아니라, 양자화 수준에 따라 한국어 인식 품질이 체감할 만큼 달라지는지를 보는 정성 비교입니다. 영수증 한 장으로 "Q4가 항상 충분하다" 같은 일반 결론을 내리면 안 됩니다. 결과를 공유할 때도 표본이 몇 장이었는지 같이 적습니다.

고르는 기준은 작업이 정합니다

원래 질문은 "한국어 영수증 OCR이라는 구체적인 작업에서 Q4로 충분한가, FP16까지 올려야 하는가"였습니다. 위 표를 채운 뒤 내 작업에서 틀리면 안 되는 필드(예를 들어 가계부라면 금액과 날짜)가 가장 작은 버전에서도 정확하면 그 버전을 쓰고, 그렇지 않을 때만 한 단계씩 올립니다. 판단의 근거는 다른 사람의 순위표가 아니라 내 작업에서 채운 표입니다.

결과를 남길 때 함께 적을 것

양자화 비교 결과는 장비와 조건이 빠지면 다른 사람이 쓸 수 없는 숫자가 됩니다. 장비나 도구 버전이 바뀌면 같은 숫자가 나온다는 보장이 없기 때문입니다. 결과 표 위에는 최소한 다음을 적어 둡니다.

  • 장비 이름, 칩 구성(CPU, GPU 코어 수), 통합 메모리 용량과 대역폭
  • OS 버전과 추론 도구, 그리고 도구의 정확한 버전 번호. "최신 버전"이라고만 적으면 몇 달 뒤에는 어느 버전이었는지 알 수 없습니다
  • 비교한 모델 태그 전체 이름(qwen3-vl:8b-instruct-q8_0처럼)
  • 프롬프트 원문과 Thinking 모드 설정
  • 입력 이미지 종류와 장 수
  • 정확도 판정 기준(정확, 부분 오류, 완전 오류)과 시간 측정 방법(3회 중간값)

이렇게 적어 두면 나중에 같은 모델의 새 버전이 나오거나 장비를 바꿨을 때 같은 표를 다시 채워 바로 비교할 수 있습니다.

체크리스트

  • 기본 태그가 어떤 양자화인지 확인했다.
  • 장비 메모리에 들어가지 않는 버전은 후보에서 뺐다.
  • 세 버전에 같은 이미지와 같은 프롬프트를 넣었다.
  • Thinking 모드를 껐다.
  • 출력 형식을 JSON으로 고정하고 유효성을 따로 확인했다.
  • 정확도를 필드별 세 단계로 기록했다.
  • 응답 시간은 3회 중간값, 메모리는 ollama ps로 쟀다.
  • 표본 수를 결과와 함께 적었다.
