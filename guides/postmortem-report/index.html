장애와 도입 시행착오, 사후 분석 문서는 이렇게 씁니다

글 Chris Jo, 2026년 10월 22일 작성

이 글은 누구를 위한 글인가

CI/CD나 클러스터를 운영하다가 장애를 겪었거나, 새 도구를 도입하며 시행착오를 많이 겪고 나서 이를 문서로 남겨야 하는 분을 위한 글입니다. 저는 Jenkins 에이전트 때문에 Minikube 노드가 통째로 멈춘 사건과, SonarQube를 Jenkins 파이프라인에 붙이며 겪은 문제들을 각각 보고서로 썼습니다. 두 문서를 쓰면서 정한 구성과 순서를 실무에서 바로 쓸 수 있게 정리했습니다.

사후 분석 문서의 목적은 같은 일이 다시 일어나지 않게 하는 것입니다. 그래서 무엇이 일어났는지보다 왜 일어났는지, 그리고 그 원인을 어떻게 확인했는지가 문서의 무게 중심이 되어야 합니다.

1단계. 문서 종류부터 고릅니다

종류다루는 것제 사례
장애 보고서사건 하나를 깊게. 원인을 확정하는 과정이 중심Jenkins 에이전트 실행 중 Minikube 전체 멈춤
도입 시행착오 보고서문제 여러 개를 넓게. 문제 목록과 다음 도입을 위한 준비물이 중심SonarQube 설치와 Jenkins 연동

둘을 섞으면 읽는 사람이 무엇을 가져가야 할지 흐려집니다. 사건 하나에 원인 하나를 좇는 글이면 장애 보고서로, 여러 문제를 차례로 풀어 간 기록이면 시행착오 보고서로 씁니다.

2단계. 장애 보고서는 이 순서로 씁니다

① 개요

발생 일시, 환경, 관련 구성요소, 증상을 한 줄씩 적습니다. Jenkins 사건이라면 2025년 10월 2일, Docker 드라이버 기반 Minikube 단일 노드, 구성요소는 Jenkins, Jenkins Agent, SonarQube Scanner, Docker Daemon, 증상은 "파이프라인 실행 중 Scanner와 Agent가 같이 돌면서 Minikube 전체가 응답하지 않음"입니다. 이 네 줄만 읽어도 어떤 사건인지 알 수 있어야 합니다.

② 시나리오

부하가 어디서 시작해 어디로 번졌는지를 텍스트 다이어그램으로 그립니다. 그림은 길게 설명하는 문단보다 빨리 읽힙니다.

[SonarQube Scanner] CPU/메모리 부하 증가
        ↓
[Jenkins Agent Pod] --docker.sock 마운트--> [호스트 Docker Daemon]
        ↓
[Minikube 노드 전체] 응답 없음

③ 원인 분석

구조 원인과 부하 원인을 나눠 적습니다. 이 사건의 구조 원인은 에이전트 Pod가 호스트의 /var/run/docker.sock을 마운트한 것이었습니다. 에이전트의 docker build가 호스트 dockerd에서 바로 실행되니 Kubernetes에 걸어 둔 requests와 limits가 아무 역할을 못 했습니다. 부하 원인은 SonarQube Scanner로, 분석 중에 CPU를 순간적으로 1코어 넘게, 메모리를 1.5~2Gi 넘게 썼습니다.

여기에 "여유 자원이 있었는데 왜 멈췄는가"라는 질문을 따로 세워 답했습니다. 단일 dockerd가 요청을 직렬로 처리하면서 생기는 락 경합, docker build가 파일을 대량으로 복사하면서 생기는 OverlayFS I/O 병목, 메모리 스파이크로 kubelet, etcd 같은 시스템 프로세스가 OOMKill되는 문제를 이유로 들었습니다. 읽는 사람이 가장 먼저 품을 반론을 문서 안에서 미리 다루면, 원인 분석이 "리소스를 늘리자"로 끝나지 않습니다.

④ 트러블슈팅 과정

원인을 어떻게 확정했는지 단계별로 적습니다. 이 부분이 문서의 신뢰도를 정합니다.

  1. kubectl top pods와 docker stats로 사용량을 보니 Scanner의 CPU와 메모리가 급격히 올랐습니다.
  2. 에이전트 Pod 안에 /var/run/docker.sock이 있고 docker build가 실행되는 것을 확인했습니다.
  3. 같은 조건에서 에이전트 없이 Scanner만 돌리자 정상이었습니다.
  4. 소켓 마운트를 빼고 에이전트를 돌리자 Minikube도 정상이었습니다.

3번과 4번처럼 하나씩 빼 보는 배제 실험이 있어야 "소켓 마운트와 단일 dockerd 경합"이라는 결론을 근거와 함께 쓸 수 있습니다. 관찰만 적힌 문서는 추정으로 읽힙니다.

⑤ 영향과 ⑥ 개선 방안

영향은 보안(컨테이너가 호스트 Docker를 완전히 제어할 수 있음), 리소스(Kubernetes 제한이 무력화됨), 안정성(dockerd가 죽으면 단일 노드 클러스터 전체가 죽음)으로 나눴습니다. 개선 방안은 영향 항목과 짝이 맞게 씁니다. 소켓 마운트 제거, Kaniko나 rootless BuildKit, Buildah 같은 Pod 내부 빌드 도구로 전환, Scanner와 Agent 모두에 requests와 limits 지정, 빌드 워크로드를 별도 노드로 격리, dockerd와 kubelet, OverlayFS I/O 지표 모니터링을 적었습니다.

⑦ 결론

한 문단으로 끝냅니다. 이 사건의 결론은 "리소스 여유는 멈추는 빈도를 낮출 뿐 같은 dockerd를 나눠 쓰는 구조적 위험은 없애지 못한다. 소켓 마운트를 빼고 Kubernetes 안에서 빌드하는 방식으로 바꿔야 한다"였습니다.

3단계. 도입 시행착오 보고서는 문제 목록 표로 시작합니다

SonarQube 도입 보고서는 환경과 목표를 적은 뒤 바로 문제 목록 표를 두었습니다. 환경은 Minikube, Helm Chart로 설치한 SonarQube Community Edition, 기존 Jenkins, Flask 애플리케이션이었습니다.

구분문제심각도해결 시간
설치Helm values 구조 이해 부족중2시간
연동Jenkins에서 SonarQube 인증 실패높음4시간
네트워크Webhook 연결 실패높음3시간
성능메모리 부족으로 분석 실패중1시간
설정Quality Profile과 Quality Gate 혼동낮음1시간
문서화설치 방법 변경(Docker Compose에서 Helm으로)중2시간

해결 시간 열을 꼭 넣기를 권합니다. 합치면 13시간이고, 그중 7시간이 인증과 Webhook에 들어갔습니다. 다음 도입 때 어디에 시간을 먼저 써야 하는지가 이 열에서 보입니다.

표 다음에는 이슈마다 문제, 원인, 해결, 실제로 바꾼 설정 조각을 적습니다. 예를 들어 인증 실패는 HTTP 401이었고 원인은 잘못된 토큰 종류, 만료된 토큰, 토큰 앞뒤 공백이었습니다. User Token을 새로 만들어 Jenkins Credentials에 secret text로 넣어 해결했습니다. Webhook은 Minikube 안의 Pod에서 호스트의 Jenkins로 접근하지 못해 Quality Gate 결과를 받지 못하고 시간 초과가 났고, 주소를 http://host.minikube.internal:8080/sonarqube-webhook/로 바꿔 풀었습니다. 메모리 부족은 -Xmx1536m -Xms512m와 limit 2048M으로, CPU 부족으로 10분이던 분석이 25분까지 늘어난 문제는 CPU limit 상향과 Quality Gate 대기 시간 15분 설정으로 정리했습니다. 설정 조각을 그대로 붙여 두면 다음 사람이 같은 값을 다시 찾지 않아도 됩니다.

마지막으로 개별 원인을 묶어 근본 원인 범주를 적습니다. 이 도입에서는 문서화 부족(Compose에서 Helm으로 바뀐 설치 방법이 반영되지 않음), 로컬과 Minikube의 환경 차이, Webhook과 Scanner 동작 방식에 대한 이해 부족, 네트워크와 리소스 사전 검증 부족 네 가지였습니다. 이 범주가 다음 도입의 사전 체크리스트가 됩니다.

작은 문제도 보고서에 남겨야 하는 이유

표에 올리기 망설여지는 작은 문제도 다음 사람에게는 같은 시간을 아껴 줍니다. SonarQube 보고서에 남긴 것 중 다시 볼 만한 것들입니다.

  • 개념 혼동. 처음에는 Quality Profile을 품질 기준, Quality Gate를 규칙으로 이해했습니다. 실제로는 Profile이 분석 규칙이고 Gate가 통과 기준입니다. 심각도는 낮지만 같은 혼동을 겪을 사람이 있어 표에 넣었습니다.
  • 경로 혼동. Webhook 주소에서 /sonar-webhook/과 /sonarqube-webhook/을 헷갈렸습니다. 플러그인 표준 경로인 /sonarqube-webhook/으로 맞췄습니다.
  • 저장소 설정. persistence를 끈 채 설치해 재시작하면 데이터가 사라졌습니다. persistence를 켜고 StorageClass를 지정했습니다.
  • 너무 엄격한 기본 Gate. 기본 Quality Gate로는 빌드가 전부 실패했습니다. 조건을 단계적으로 올리고 sonar.exclusions로 레거시 폴더를 빼는 것으로 정리했습니다. 해결 방법까지 적어 두어야 다음 도입 때 같은 판단을 처음부터 다시 하지 않습니다.

장애 보고서에서도 같은 원칙을 씁니다. "Scanner가 CPU를 많이 썼다"는 관찰이고, 배제 실험으로 확인한 "소켓 마운트와 단일 dockerd 경합"이 원인입니다. 관찰은 트러블슈팅 과정에, 확인된 것만 원인 분석에 두면 두 칸이 섞이지 않습니다.

체크리스트

  • 개요 네 줄(일시, 환경, 구성요소, 증상)만 읽어도 사건을 알 수 있다.
  • 부하나 요청의 경로를 그림 하나로 보여 준다.
  • 구조 원인과 부하 원인을 나눠 적었다.
  • 원인을 확정한 배제 실험이 단계별로 적혀 있다.
  • 개선 방안이 영향 항목과 하나씩 짝을 이룬다.
  • 시행착오 보고서라면 문제마다 심각도와 해결 시간이 있다.
  • 실제로 바꾼 설정 값이 문서에 그대로 붙어 있다.
  • 근본 원인을 범주로 묶어 다음 도입의 체크리스트로 바꿨다.
